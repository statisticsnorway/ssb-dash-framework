# Issues

This file tracks shared source-code issues, HB integration risks, and proposed
HB behavior enhancements. Changes to shared framework code require maintainer
approval.

| ID | Area | Issue | Current behavior or context | Impact | Proposed handling | Status |
|---|---|---|---|---|---|
| HB-PERIOD-001 | `TimeUnit.parse()` / WEEK | Canonical week periods cannot be parsed. | Parsing `2024-W01` raises `ValueError: Unsupported token: WW` because `TimeUnit.parse()` passes `YYYY-[W]WW` to Pendulum, which does not support `WW`. | Any caller configured for WEEK cannot convert canonical periods to dates; an HB resolver cannot rely on the shared parser/formatter today. | Keep the shared `TimeUnit` module unchanged for HB. The HB week helper validates canonical ISO weeks, calls `TimeUnit.parse()`, and falls back only for the known `Unsupported token: WW` error. It formats output from the ISO week-year and week number. Keep behavior regression tests and a strict-xfail round-trip sentinel; remove the fallback and sentinel when shared `TimeUnit` supports WEEK. | unresolved |
| HB-PERIOD-002 | `SelectedTimeUnit.to_str()` / QUARTER | Quarter periods are not formatted canonically. | `2024-Q1` formats as `2024-11`; subtracting one quarter and formatting produces `2023-44`. Pendulum interprets the `Q1`/`Q4` portions as format tokens rather than literal canonical text. | HB cannot emit valid canonical quarter periods for the handler or Vaskify; the issue also affects year-boundary comparisons. | Keep the shared `SelectedTimeUnit.to_str()` unchanged. In the HB period helper, format quarters from the selected date's year and month-derived quarter number as `YYYY-Qn`; keep `TimeUnit` for parsing and date arithmetic. Add HB behavior tests for Q1–Q4 and Q1-to-previous-year-Q4, plus a temporary strict-xfail test for the shared quarter round-trip. Remove the HB formatter and sentinel when the shared formatter is fixed. | unresolved |
| VASKIFY-001 | `ssb-vaskify` period validation | Half-year period strings are rejected. | `ssb-vaskify` 0.0.6 rejects `YYYY-1` and `YYYY-2`; its accepted period formats omit half-year. | Data using half-year periods cannot use Vaskify's HB API. | Add native validation and execution support for `YYYY-1` and `YYYY-2`, with package-level tests for both half-years and consecutive half-year pairs. | unresolved |
| HB-ALTINN-001 | HB / multiple active Altinn submissions | Consider giving users explicit choices when multiple active submissions exist for the same unit and period. | **Cancel** stops the current HB run. **Continue** proceeds using the latest active submission for each affected unit and period, with a message that explains this default. **Custom** lets the user choose a submission for an affected unit-period. | The approved baseline is to use `active_no_duplicates_refnr_list` unchanged with the configured form and period-specific filters, once for each comparison period. Do not change the shared helper for this proposal. Define how ties or missing `dato_mottatt` values are presented before implementation. | Proposed; requires project-owner review |
| HB-ALTINN-002 | HB / active-submission period scoping | The existing helper deduplicates active submissions by `ident`, not by period. | `active_no_duplicates_refnr_list` sorts active submissions by `dato_mottatt` and keeps the first row for each `ident`. If it receives candidates from both comparison periods in one call, it can discard one period's submission for that identifier. | The HB input may be missing one of its required comparison-period rows. | Use the helper unchanged with the configured form and period-specific filters, once per comparison period. Do not change the shared helper for HB. | Workaround approved; cover in Altinn adapter tests |
| FRAMEWORK-VALIDATION-001 | Framework / validation conventions | Validation conventions differ between modules. | HB data-contract validation raises `TypeError` or `ValueError`; NSPEK UI validation returns a validity/message pair; Data Editor and Building Blocks use Pydantic for configuration. There is no single cross-module convention for choosing or placing validation. | Different patterns can increase cognitive load and make it less predictable where to add checks or how failures reach users as the framework gains modules. | Agree lightweight conventions by boundary and caller: use Pydantic for structured configuration, explicit validation results/messages for user-correctable UI input, and typed exceptions for invalid data or API contracts. Keep domain rules with their owning module and share helpers only for identical invariants. Apply conventions to new modules and revisit existing code when touched; do not introduce a generic validation framework without repeated concrete need. | Proposed; requires maintainer review |
| FRAMEWORK-VARIABLESELECTOR-001 | `VariableSelector` / configured `TimeUnit` | Modules cannot retrieve the configured `TimeUnit` through a public accessor. | `VariableSelector.get_timevar(...)` returns a Dash dependency; the configured `TimeUnit` is held in private class state. | A module needing the configured frequency must duplicate configuration or couple itself to private state. | Consider a public `VariableSelector.get_configured_time_unit()` accessor that returns the configured `TimeUnit` and raises clearly when unset. Keep module-local implementations independent until this shared API is approved. | Proposed; requires maintainer review |
| DATA-001 | Shared data model / surrogate keys | Explore whether stable internal surrogate keys could simplify joins between related records. | Altinn relationships currently use natural keys such as `(iso_periode, skjema, ident)` and `refnr`. Tables have individual row IDs, but these do not replace the relationship keys. | Repeating composite join conditions can increase query complexity and the risk of inconsistent joins. Generating unrelated IDs per row would not solve this. | Ask maintainers to assess a persisted, stable key mapping or curated staging layer, including migration and write-path implications. Keep natural-key constraints and current HB behavior unchanged unless an approach is approved. | Proposed; requires maintainer review |
| HB-METHOD-GUIDANCE-001 | HB / Data Editor guidance | Provide HB-specific guidance about which values are within the method's scope. | The HB result identifies candidate values, but the Data Editor has no method-supplied contextual text field for explaining valid scope. | Users lack guidance when deciding whether a flagged value should be changed; an automated "best value" could be mistaken for a verified correction. | Add or assess a contextual help-text field in the Data Editor that HB can populate with scope guidance. Keep the guidance separate from any recommendation of a replacement value. | Requested; not implemented |
| HB-METHOD-RESULT-REFRESH-001 | HB / Data Editor refresh | Refresh HB results after a successful Data Editor save. | After returning from the Data Editor, HB results can reflect the prior data until the user reruns the method. | Users may mistake stale results for results based on the saved values. | Provide a reliable save-completed signal so HB can rerun against saved data, or visibly mark results stale until refreshed. Coordinate with the Data Editor and prevent overlapping or outdated runs. | Requested; not implemented |
| DATA-EDITOR-001 | Data Editor / save state | Enable the save action immediately after an edit. | **Lagre redigering** remains unavailable until blur or another action occurs after changing a value. | The extra step is confusing and can make edits appear unsavable. | Update the editor's dirty-state or callback behavior so the save action becomes available when the value changes. | Requested; not implemented |
| DATA-EDITOR-002 | Data Editor / deletion | Support deleting a data point. | The editing workflow does not provide a delete action. | Users cannot remove a point when deletion is the intended correction; deleting also affects the analysis population and audit history. | Define deletion semantics, confirmation, and audit behavior before implementation; distinguish deletion from changing a value. | Requested; not implemented |
| DATA-EDITOR-003 | Data Editor / reason prefill | Support pre-filling the reason for an edit. | The reason is entered manually even when the flow may have relevant context or a recent selection. | Repeated manual entry adds friction to the editing flow. | Evaluate retaining the user's last reason selection temporarily or passing explicit context from the Variable Selector. Keep the reason visible and editable, and record the final user-confirmed value. | Requested; not implemented |
| FRAMEWORK-FIGURE-001 | Shared UI / figure sizing | Resize figure windows/components when the Variable Selector is shown. | The Variable Selector can cover part of the HB graph. | Part of the plotted result becomes obscured. | Make figure windows/components respond to the available layout width when the Variable Selector is open; verify the behavior in the HB demo and other figure-based modules. | Requested; not implemented |
| Wish0001 | Variable View / editing | Allow users to edit values from Variable View. | Corrections currently require navigating to the Data Editor. | Direct editing could reduce navigation and context switching. | Assess inline value editing while preserving the Data Editor's reason and justification flow. | Wish; not implemented |
