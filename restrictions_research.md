# HB restriction and usability inventory

## Scope and status

This document records the restriction inventory, classification, user impact,
evidence, timing investigation, and recommendations for approved tasks 16.1
through 16.5 in [plan.md](plan.md). It documents current behavior only.
Recommendations below are for user approval; no runtime behavior was changed.

## Preliminary user assessment

The initial assessment is that most current restrictions are justified for
V1, but further investigation is needed. This is not a blanket confirmation
of every restriction or approval to relax any of them. The pending timing
investigation and evidence-based recommendations remain necessary.

## HB input and comparison contract

| Restriction and enforcement | Classification | Real-world use case blocked or affected | Evidence for keeping it | Candidate less-restrictive alternative |
|---|---|---|---|---|

Aggregation has no established methodological basis. |
| Periods must be canonical for a framework `TimeUnit`; when configured, the period frequency must match it. ## Altinn retrieval and normalization

| Restriction and enforcement | Classification | Real-world use case blocked or affected | Evidence for keeping it | Candidate less-restrictive alternative |
|---|---|---|---|---|
| Production retrieval requires a configured form and an exact mapping from each selectable HB variable to a `feltsti`; an unmapped variable fails rather than guessing a field. | Data-integrity safeguard | A new field cannot be analyzed until its exact source mapping is configured. Similar or renamed fields are not discovered automatically. | [altinn_candidate_retrieval.py](src/ssb_dash_framework/modules/hb/altinn_candidate_retrieval.py) validates the configuration and raises when no mapping exists; [test_hb_altinn_data_handler.py](tests/unittests/module_tests/test_hb_altinn_data_handler.py) verifies unmapped strata fail before database access. | Provide a configuration validation/listing workflow that helps map fields. Fuzzy matching is not a safe substitute for an exact mapping. |
| Per comparison period, the existing helper selects the latest active submission per identifier, based on receipt time. HB invokes it separately for each period. | Data-selection policy / method assumption | Earlier still-active submissions are not available to the run; users cannot choose a specific submission or compare revisions. | [core_query_functions.py](src/ssb_dash_framework/utils/core_query_functions.py) implements the latest-active rule. [altinn_candidate_retrieval.py](src/ssb_dash_framework/modules/hb/altinn_candidate_retrieval.py) scopes each call by period; [test_hb_altinn_active_selection.py](tests/unittests/module_tests/test_hb_altinn_active_selection.py) covers latest-per-period selection. | Show the selected submission reference and receipt context, or support an explicit submission-selection policy, after confirming the product and audit requirements. |
| A scoped unit-period without an active submission causes the handler to fail the run rather than omit that period silently. | Data-integrity safeguard | One missing active submission can block analysis of otherwise available units and periods. | [altinn_candidate_retrieval.py](src/ssb_dash_framework/modules/hb/altinn_candidate_retrieval.py) compares expected and selected unit-periods; [test_hb_altinn_active_selection.py](tests/unittests/module_tests/test_hb_altinn_active_selection.py) and [test_hb_altinn_data_handler.py](tests/unittests/module_tests/test_hb_altinn_data_handler.py) assert the missing unit and period are reported. | Consider an explicit partial-coverage mode that retains missing unit-periods and warns about coverage. It would change the analysis population and needs method approval; it is not an automatic safe fallback. |
| More than one exact-path measure answer is not resolved by first row, aggregation, or `dybde`/`indeks`: the value becomes missing and a structured warning is recorded. | Data-integrity safeguard with presentation impact | A potentially usable repeated-field response is excluded from that unit-period's calculation unless an unambiguous answer-selection rule exists. | [altinn_normalization.py](src/ssb_dash_framework/modules/hb/altinn_normalization.py) implements the missing-value plus warning behavior; [test_hb_altinn_normalization.py](tests/unittests/module_tests/test_hb_altinn_normalization.py) asserts it. The approved design says downstream methodology owns missing-value treatment. | Add explicit answer-selection configuration (for example, approved depth/index criteria) if the form semantics define one. Do not select the first answer or aggregate by default. |
| A missing measure answer is retained as a missing numeric value without a structured warning; malformed non-null values (including booleans or non-real values) raise and abort normalization. | Data-integrity safeguard; missing-answer path is a presentation behavior | Missing answers can make units not comparable without identifying the missing source answer to the user. One malformed answer can prevent the entire run. | [altinn_normalization.py](src/ssb_dash_framework/modules/hb/altinn_normalization.py) distinguishes missing from invalid values; [test_hb_altinn_normalization.py](tests/unittests/module_tests/test_hb_altinn_normalization.py) verifies both missing preservation and conversion errors. | Consider a structured warning for missing answers and, separately, converting an invalid cell to missing plus a warning. Continuing after invalid conversion can change the population; require method approval before doing so. |
| When strata is configured, Altinn requires exactly one non-null, non-blank scalar strata answer for every returned unit-period. Missing, repeated, or invalid strata is blocking; there is no automatic unstratified fallback. | Data-integrity safeguard and method assumption | Blocks stratified analysis when group membership is incomplete or ambiguous, even if measure values are available. | `_get_altinn_hb_strata_value` in [altinn_normalization.py](src/ssb_dash_framework/modules/hb/altinn_normalization.py) enforces the rule; [test_hb_altinn_normalization.py](tests/unittests/module_tests/test_hb_altinn_normalization.py) covers missing, null, blank, and multiple answers. The detailed architecture explicitly rejects unknown-group or unstratified fallback. | Offer unstratified analysis only as an explicit, separately confirmed run choice, or define an approved unknown-stratum policy. Either changes reference groups and requires method approval. |

## Vaskify preflight, strata, and result contract

| Restriction and enforcement | Classification | Real-world use case blocked or affected | Evidence for keeping it | Candidate less-restrictive alternative |
|---|---|---|---|---|
| Configured strata must exist as `strata` in the input and have one consistent value per unit across both periods. | Vaskify API limitation and method assumption | Blocks comparisons where units change strata between periods, such as a reclassification, merger, or transfer. | `_validate_hb_vaskify_input` in [vaskify.py](src/ssb_dash_framework/modules/hb/vaskify.py) rejects missing or changing strata before `Detect`; [test_hb_vaskify.py](tests/unittests/module_tests/test_hb_vaskify.py) checks both. The detailed architecture documents that Vaskify 0.0.6's wide/grouping behavior cannot safely choose one period's group. | Support changing strata only after defining which period's group governs the comparison or Vaskify supports period-varying groups natively. No safe default is established. |
| The adapter requires Vaskify's expected result columns, including both period values, limits, `ratio`, `median_ratio`, and `flag_hb`; result IDs must be non-null unique strings drawn from the input. Subsets of input IDs are accepted. | Vaskify API contract and data-integrity safeguard | Blocks an API version or configuration that changes the output schema or emits ambiguous/unknown identifiers, even if some diagnostics could still be shown. | `_validate_hb_vaskify_result` in [vaskify.py](src/ssb_dash_framework/modules/hb/vaskify.py) enforces the schema and identifiers; [test_hb_vaskify.py](tests/unittests/module_tests/test_hb_vaskify.py) covers missing columns, invalid IDs, and accepted subsets. | Add a versioned compatibility adapter if Vaskify changes its public schema. Keep stable-ID validation; only make diagnostics optional after defining how the UI handles their absence. |
| Vaskify parameters are explicit fixed values (`pu=0.5`, `pa=0.05`, `pc=20`, quartiles, wide output, all-scope); the module exposes no per-run controls. | Method assumption / API configuration | Blocks users from running approved alternative parameterizations or alternate output scopes from the UI. | `run_hb_vaskify` in [vaskify.py](src/ssb_dash_framework/modules/hb/vaskify.py) passes these values explicitly; tests assert the exact call. Architecture documents them as public defaults, not methodology approval for alternatives. | Expose parameters only after the method owner defines supported values, semantics, validation bounds, and result compatibility. |
| Vaskify may omit units with no diagnostics. The normalizer preserves input units and leaves diagnostics/flags missing; the UI counts these as not comparable rather than converting them to flag `0`. | Vaskify method behavior plus presentation behavior | Users can see how many units are not comparable but not necessarily why each one lacks a diagnostic. | `normalize_hb_result` in [vaskify.py](src/ssb_dash_framework/modules/hb/vaskify.py) reconciles by `unit_id`; the HB result view counts missing flags in [hb_method.py](src/ssb_dash_framework/modules/hb_method.py). Tests cover subset outputs and not-comparable normalization. | Display unit-level reasons only if Vaskify or a separately validated rule can supply them. Do not infer a reason from missing diagnostics alone. |
| An entirely empty Vaskify result is rejected as a failed run, not displayed as a successful run with zero flagged units. | API limitation and presentation safeguard | Blocks a “no comparable units” result from appearing as a completed analysis; the user instead receives the generic run-failure alert. | The installed Vaskify 0.0.6 behavior and empty result are documented in [ssb-vaskify-design.md](ssb-vaskify-design.md). `run_hb_vaskify` and `normalize_hb_result` reject empty results; [test_hb_vaskify.py](tests/unittests/module_tests/test_hb_vaskify.py) covers it. An empty frame does not distinguish no eligible population from another unsuccessful result. | Prefer a distinct no-comparable outcome only when Vaskify exposes a reliable structured status or an approved preflight can establish it without reimplementing eligibility. Do not reinterpret empty output as “no outliers.” |
| Normalization rejects source context that collides with generated value columns or Vaskify diagnostic columns. | Data-integrity safeguard | Blocks a source adapter from preserving a context field named like `ratio`, `flag_hb`, or a generated `value_<period>` column. | Collision checks in [vaskify.py](src/ssb_dash_framework/modules/hb/vaskify.py) prevent silent replacement; [test_hb_result_normalization.py](tests/unittests/module_tests/test_hb_result_normalization.py) covers context collisions. | Namespace source context columns or apply an explicit stable renaming map, while preserving the original field meaning. |

## User-visible outcomes

| Restriction and enforcement | Classification | Real-world use case blocked or affected | Evidence for keeping it | Candidate less-restrictive alternative |
|---|---|---|---|---|
| Handler warnings are shown as one aggregate count; on successful runs, structured details are stored but not rendered. If a later Vaskify step fails, the callback returns `None`, so the details are not stored with a result. | Presentation behavior | Users cannot identify affected unit-periods from the alert. On a later failure, they receive the count and a generic error, but cannot access the structured warning records. | `_execute_hb_run` in [hb_method.py](src/ssb_dash_framework/modules/hb_method.py) alerts with the count before Vaskify and only includes details in its return value after normalization succeeds. The exception handler clears the store by returning `None`. | Defer warning presentation until the run outcome is known; show the count with the final status and provide an access-appropriate detail view if row-level identifiers may be exposed. |
| Run exceptions are logged with limited context and shown as the same generic user-facing error, regardless of whether the failure is invalid selection, Altinn data, Vaskify preflight, or Vaskify execution. | Presentation behavior and privacy safeguard | Users cannot tell which corrective action is appropriate from the alert; operational diagnosis also requires protected logs. | The run callback in [hb_method.py](src/ssb_dash_framework/modules/hb_method.py) catches exceptions and shows a generic message, while logging only selected context and exception type. | Map known exception categories to specific safe messages while preserving sanitized logs. Do not expose exception text or row-level data without a privacy review. |

## Validation and warning timing

| Restriction or warning | Detection point in the run | Current user-visible effect | Timing finding |
|---|---|---|---|
| Invalid selected variable or period | At the start of `_execute_hb_run`; canonical period resolution is before handler access. | Generic failure alert; no data query for these errors. | Early. No timing change indicated. |
| HALF_YEAR unsupported by installed Vaskify | `get_hb_dataframe` is called first; `run_hb_vaskify` then rejects HALF_YEAR before constructing `Detect`. | Altinn retrieval and normalization may already have run; the outer callback shows the generic run-failure alert. | Avoidably late. The selected frequency is known before source access. |
| Missing active submissions, malformed measure values, or missing/ambiguous strata | During Altinn retrieval, active-submission coverage validation, or answer normalization. | Handler raises; outer callback shows the generic run-failure alert. Details are not shown to users. | Data-dependent and discoverable only after source access. Safe error categories could improve feedback without exposing row-level values. |
| Ambiguous measure answer | During Altinn normalization after candidate retrieval and active-submission selection; the handler returns a warning and missing value. | `_execute_hb_run` sends an ephemeral warning count before Vaskify preflight and calculation. | The source warning is emitted before run success is known. If a later step fails, the user sees the warning followed by a generic failure; warning details are not returned to the store. |
| HB input, period-level, configured-strata, or changing-strata preflight failure | In `run_hb_vaskify`, after the handler has returned and after any handler warning alert, but before `Detect`. | Generic failure alert. A source warning may already have appeared for this failed run. | Some checks require the returned data; ordering them before warning presentation is feasible without relaxing the checks. |
| No eligible Vaskify output | Only after `Detect.hb()` runs. Vaskify 0.0.6 logs an error and returns an empty result; the helper raises. | Generic failure alert; it is not shown as a successful run with no flagged units. | Inherently late without duplicating method eligibility. The framework cannot safely precompute Vaskify's positive-value eligibility. |
| Incompatible Vaskify result shape | After `Detect.hb()` returns, during result validation. | Generic failure alert. | Output-dependent; a call or package compatibility check is required to observe the result. |
| Source-context/normalized-result column collision | During `normalize_hb_result`, after a non-empty Vaskify result is returned. | Generic failure alert after Vaskify has already run. | The known generated-column collisions are determinable from input context and comparison periods before Vaskify; checking them earlier can avoid wasted calculation without changing acceptance. |

### Findings

1. The HALF_YEAR guard is the clearest avoidably late restriction: the
   unsupported frequency is known before the Altinn handler is called.
2. Handler warnings are emitted before Vaskify preflight and execution. A
   warning can therefore precede a failure; the user gets only a count, and
   the structured details are lost from the result store when the run fails.
3. Source-content errors (active coverage, malformed values, and strata
   answers) cannot be known until Altinn data is read. They currently collapse
   into the same generic alert as Vaskify failures.
4. Vaskify eligibility and output emptiness are known only after its call.
   Pre-filtering or interpreting empty output in the framework would duplicate
   method logic or turn an ambiguous API result into a success.
5. Normalized-column collisions are predictable before the Vaskify call and
   can be checked earlier while retaining the same rejection.

## Recommendations for user approval

These recommendations address timing and feedback; they do not relax any
approved data, period, strata, or methodology restriction.

Estimated scale is a rough engineering-scope estimate, not a calendar-time
commitment: **Small** is a localized change with focused tests; **Medium**
touches multiple run-flow steps or needs a small refactor and broader tests;
**Large** would span modules or alter a public/data contract.

| Priority | Recommendation | Effect | Estimated implementation scale | Boundary |
|---|---|---|---|---|
| High | Check known Vaskify frequency support before calling the data handler. | Reject HALF_YEAR at the earliest deterministic point, avoiding unnecessary Altinn retrieval and a late generic failure. | **Small** — move/add the same preflight at the run boundary and cover that the handler is not called. | Keep the same HALF_YEAR rejection until native Vaskify support is verified. |
| High | Delay handler-warning alerts until the run has a terminal outcome. | On success, show the aggregate warning with the result; on failure, report both the safe failure category and that source warnings occurred. Preserve structured details in an access-appropriate location instead of dropping them on failure. | **Medium** — coordinate warning delivery with success/failure handling and retain warning information on failure; add callback outcome tests. | Keep alert summaries free of row-level identifiers unless a suitable detail surface is approved. |
| Medium | Run deterministic common-input and normalized-column checks before Vaskify, and before presenting handler warnings. | Avoid a warning-then-failure sequence and avoid running Vaskify when known output-column collisions will prevent normalization. | **Medium** — factor/reuse preflight checks across handler result, Vaskify call, and normalization with regression tests. | Reuse existing validation rules; do not weaken them or duplicate Vaskify's statistical checks. |
| Medium | Replace the single generic run-failure message with safe, categorized messages for known validation, Altinn-data, Vaskify-preflight, and Vaskify-result failures. | Tell users what kind of correction is needed while retaining privacy-safe logs. | **Medium** — define/map safe failure categories and test each public message without exposing exception or row data. | Do not display exception text, raw values, or row-level identifiers in transient alerts. |
| Guardrail | Keep Vaskify eligibility and empty-result interpretation inside the Vaskify boundary. | Avoid false “no outliers” success and avoid changing the comparison population by framework-side filtering. | **No implementation** — preserve current behavior; revisit only with a reliable Vaskify status or approved contract. | Only add a distinct no-comparable outcome if Vaskify provides a reliable status or an approved, non-duplicative contract. |

## Limits of this assessment

The evidence establishes current code order, tested behavior, and documented
Vaskify 0.0.6 behavior. A candidate alternative is not proof that it preserves
HB population, reference groups, thresholds, or classifications. Any proposal
that changes analysis eligibility or strata semantics requires method-owner
review and separate user approval. No runtime changes were made as part of this
investigation.
